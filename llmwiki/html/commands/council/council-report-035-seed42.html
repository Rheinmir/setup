Phá tiền đề 'cần registry riêng'. Guard `[ -d llmwiki ]` hiện tại đã CHỌN LỌC gián tiếp: chỉ repo có llmwiki/ mới gác — mà llmwiki chỉ xuất hiện khi user CHẠY bootstrap.

Vậy 'đã bootstrap' ≈ 'có llmwiki'. Registry riêng (guarded-repos.json) THÊM một nguồn chân lý PHẢI đồng bộ với thực tế đĩa — nó DRIFT: user xóa repo/đổi path → registry trỏ ma; clone máy khác → registry không có entry → không gác dù có llmwiki.

Hỏi: registry giải quyết case THẬT nào mà `[ -d llmwiki ] && [ -f llmwiki/.harness-stamp ]` không? Nếu chỉ cần 'repo opt-in gác', thì STAMP TRAVEL trong repo (đi theo clone) đủ và KHÔNG drift — guard = 'có stamp'.

Registry global là state trùng lặp, rủi ro đồng bộ. Ưu tiên: guard-by-stamp (travel, self-describing), bỏ registry global.

Nghịch đảo: cái gì làm registry global thất bại? (a) Hai nguồn chân lý (registry ↔ đĩa) LUÔN drift — repo move/rename/delete, registry thành nghĩa địa path chết.

(b) Clone sang máy mới: registry KHÔNG travel → repo có llmwiki+stamp mà máy mới không biết gác → SILENT không bảo vệ (rủi ro tệ nhất: tưởng gác mà không). Socrates đúng: stamp TRAVEL trong repo là nguồn chân lý tự-mô-tả, không drift.

NHƯNG global VẪN cần cho MỘT việc: engine + version (update-once). Vậy tách bạch: GLOBAL = engine + version.json (dùng chung, self-update); REPO = stamp .harness-stamp (travel, 'tôi gác theo vX'); GUARD = `[ -f llmwiki/.harness-stamp ]` (đọc stamp travel, KHÔNG registry).

Registry global chỉ là CACHE tiện tra 'máy này gác repo nào' — nếu build, phải rebuildable từ scan đĩa, KHÔNG phải nguồn chân lý.
